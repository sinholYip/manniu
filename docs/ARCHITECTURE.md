# 架构说明

本文说明 man牛 的分层结构、依赖方向与关键设计取舍。改动代码前建议先读一遍。

## 整体形态

单模块 Android 应用（`:app`），Jetpack Compose 构建界面，Room + SharedPreferences 持久化，
无后端、无账号体系，全部数据留在设备本地。

```
┌─────────────────────────────────────────────┐
│  ui/screen      首页 · 训练 · 我的            │  页面
├─────────────────────────────────────────────┤
│  ui/components  弹窗 · 表单控件               │  可复用组件
├─────────────────────────────────────────────┤
│  ui/theme       颜色 · 字号 · 形状            │  设计令牌
├─────────────────────────────────────────────┤
│  data           Room · 本地存储 · 备份 · 食物库 │  数据访问
├─────────────────────────────────────────────┤
│  core           热量与宏量换算                │  纯计算
├─────────────────────────────────────────────┤
│  model          数据模型 · 派生规则            │  纯数据
└─────────────────────────────────────────────┘
```

依赖只能**自上而下**。`model` 与 `core` 不依赖任何上层，也不依赖 Android 框架，
因此可以被纯 JVM 单元测试直接覆盖 —— 这也是这两层的测试覆盖率最高的原因。

## 包职责

| 包 | 职责 | 关键文件 |
| --- | --- | --- |
| `com.ranke.health` | 应用入口与页面路由 | `MainActivity.kt` |
| `com.ranke.health.model` | 数据模型、枚举、派生计算（如训练统计、周期生成） | `Models.kt` |
| `com.ranke.health.core` | 无副作用的热量与宏量换算 | `CalorieMath.kt` |
| `com.ranke.health.data` | Room 实体与 DAO、本地存储、备份序列化、食物数据源 | `AppDatabase.kt`、`LocalStore.kt`、`DataBackup.kt`、`FoodCatalogRepository.kt` |
| `com.ranke.health.ui.theme` | 设计令牌：颜色、字号、圆角、间距、日期格式 | `Theme.kt` |
| `com.ranke.health.ui.components` | 跨页面复用的弹窗与表单控件 | `Dialogs.kt` |
| `com.ranke.health.ui.screen` | 完整页面及其私有子组件 | `DashboardScreen.kt`、`TrainingScreen.kt`、`ProfileScreen.kt` |

## 数据流

用户操作 → 页面事件回调 → `LocalStore` 写入 Room / 偏好 → 返回新的状态快照 → Compose 重组。

状态由 `MainActivity` 持有并通过参数下传给各页面，页面本身不持有数据源。
刻意没有引入 ViewModel 与依赖注入框架：当前页面数量与状态复杂度不足以摊薄这些抽象的
引入成本，单层持有 + 显式回调更容易追踪数据从哪里来、到哪里去。当出现跨页面共享的
异步数据流（例如接入云同步）时，再引入 ViewModel 会更划算。

## 关键设计取舍

**热量始终由三大营养素反算。** 碳水 ×4、蛋白质 ×4、脂肪 ×9，不允许单独填写热量值，
避免出现"三项加起来对不上总数"的数据。见 `CalorieMath.kt`。

**备份格式是跨端契约。** `schemaVersion: 1` 的 JSON 同时被 Android 版与微信小程序版读取。
修改结构必须递增版本号并保留旧版本解析路径，否则降级安装会丢历史数据。恢复前先完整校验，
校验失败时**不写入任何数据**。

**Room 写入合并到单事务。** 恢复流程涉及多表写入，中途失败必须整体回滚，
不能留下"体重恢复了但饮食没有"的半截状态。

**训练计划以日期为主键，而非星期。** 早期用"每周固定训练日"表达，无法支持挪动训练日、
临时休息和周期性减载。改为按日期编排后，饮食目标由当天的训练 / 休息标记驱动，
两个模块的联动规则因此收敛到一处。

**设计令牌集中管理。** 颜色（含红涨绿跌语义色）、字号、圆角、间距、日期格式全部收在
`ui/theme/Theme.kt`，页面里不出现魔法值。

## 测试策略

| 层 | 方式 | 说明 |
| --- | --- | --- |
| `model` / `core` | 纯 JVM 单测 | 边界值、周期生成、去重规则 |
| `data` | Robolectric + 内存 Room | 备份恢复的失败不改数据、重复恢复去重 |
| `ui` | Compose UI 测试 | 关键交互（如动作行布局） |

> **本机路径必须为纯 ASCII。** 工程放在含中文的目录（如 `D:\工程\manniu`）时，
> Gradle 传给测试进程的类路径会解析失败，表现为所有测试报
> `ClassNotFoundException` + `initializationError`，但编译正常。
> 这是 AGP 对非 ASCII 路径的已知限制（`android.overridePathCheck=true` 只是屏蔽了警告）。
> 判断方法：把同一份代码复制到 `C:\tmp\` 下运行，测试即可通过。
> **CI 运行在 Linux 的 ASCII 路径上，所以 CI 绿而本地红，通常就是这个问题。**

## 有意不做的事

- 不引入 Hilt / Koin：当前依赖图很浅，手动传参更直观。
- 不拆多模块：单模块编译约 30 秒，拆模块带来的构建复杂度大于收益。
- 不做网络同步：产品定位是本地优先，联网只在用户主动搜索食物时发生。
